# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Generates a 4-year course plan for University of Maryland students. It takes completed courses, AP credits, transfer credits and degree requirements into account. The `optimizer/` package is the library. The command-line entry point is `optimizer/cli.py` (`umd-plan`, also `main.py`): `plan`, `audit` and `alternatives` subcommands over a student profile JSON (`optimizer/data/profile.py`, format in its docstring; examples in `examples/profiles/`). `optimizer/report.py` `format_audit(program, report, catalog, schedule=None)` renders a `ScheduleOptimizer.audit` report as text by program (majors with their benchmarks, minors, gen-eds, degree credits and unique credits, requests); it relies on that report's row order (owned requirements, benchmarks, requests) and leaves out GROUPs that ask for nothing (the CS area labels). `umd-plan audit` prints it, against credited courses or with `--plan` a generated plan. `optimizer/export.py` (`to_markdown`, `to_csv`, `to_ical`) exports plans for `umd-plan plan --format`/`-o FILE` (format from the extension); iCal events span approximate term dates (`TERM_DATES`), lines are CRLF and folded at 75 octets. Other top-level directories: `examples/` (demo scripts and `profiles/`), `scripts/` (ad-hoc debug helpers), `scrapers/` (data acquisition), `data/` (raw scraper output, department lists, scrape logs) and `docs/` (notes and requirement source material).

## Commands

The project uses `uv` (`pyproject.toml`, `uv.lock`, Python 3.13 from `.python-version`). Dependencies: `networkx`, `ortools` (the CP-SAT scheduler; optional at runtime, the greedy plan is used without it), `pytest`, and `requests`/`beautifulsoup4` (scrapers only).

```bash
uv sync                                   # install deps
uv run pytest                             # all tests (~3 min: every full plan runs the solver, ~1-6 s each)
uv run pytest tests/test_optimizer.py::test_prerequisite_simple   # single test
uv run pytest -s tests/test_cs_major_general_track.py            # prints the generated schedule
uv run python examples/example_full.py    # end-to-end demo against sample_data/
uv run umd-plan plan examples/profiles/cs_freshman.json   # CLI (also: audit, alternatives; --json, --no-solver)
```

The `run-stack` skill (`.claude/skills/run-stack/SKILL.md`) has the full run guide: a `uv` fallback when it isn't installed, what normal planner output looks like, and safe scraper usage.

Run everything from the repo root. Several scripts and tests load data with the relative path `Path("sample_data")`. `optimizer` is an installable package (hatchling, see `pyproject.toml`), and `uv sync` installs it in editable mode. That's what lets `examples/*.py` and `scripts/*.py` import it when run by path (`uv run python scripts/check_cycles.py`). pytest only collects tests from `tests/`. `scripts/debug_*.py`, `check_*.py` and `trace_optimizer.py` are ad-hoc scripts, not tests.

Scheduling must stay deterministic. `tests/test_course_selection.py::test_schedule_is_identical_across_hash_seeds` runs the planner under several `PYTHONHASHSEED`s, so never let output depend on `set`/`dict` iteration of unordered data.

## Architecture

### Pipeline (`optimizer/core/optimizer.py` → `ScheduleOptimizer.optimize_schedule`)
1. **Select courses**: `select_courses` → `CourseSelector.select` (`optimizer/core/selection.py`) returns a `Selection`: the chosen `courses`, `by_requirement` (courses per requirement, keyed by index path into `get_all_requirements()` and nested `courses`/`choices`, since `id`s can collide) and the locked `gen_ed_options`. All per-run state lives in a private `_SelectionRun`, so the selector is reentrant. It walks `StudentDegreeProgram.owned_requirements()` in order: each major's lower/upper/supporting/concentration (`primary_major`, then `additional_majors`, then `additional_degrees`, any number), each minor, gen-eds, then the degree's credit minimums (the highest any major sets; `total_credits` plus `rules.EXTRA_DEGREE_CREDITS` per extra degree), then, with several degrees, one `UNIQUE_CREDITS` per major. Each requirement comes with its `RequirementOwner` (program kind, code and, for majors, `degree`: 0 for the primary and additional majors, 1.. for `additional_degrees`; `other_degree` compares them).
   - Before any requirement, the student's `requested_courses` (`CourseRequest`: a code, optionally `by_semester`/`by_credits`) that are in the catalog and not credited go into the plan as shared, unclaimed picks (`Selection.requested`), so requirements reuse them first (`_free`) and claim them.
   - `StudentProfile.excluded_courses` (equivalents included, `_excluded`) are avoided wherever there's a choice: ranked last in `_pick_from_group` and `_select_category` (first in the key and in the single-department cost), costed like a missing course in `_option_cost`, tried last among prerequisite OR alternatives, and never picked as gen-eds or free electives. A `COURSE` requirement or all-listed GROUP still takes them.
   - `COURSE` requirements claim their course.
   - A `CHOICE` of nested requirements (the Math supporting sequences) takes the option needing the fewest courses missing from the catalog, then the fewest new courses (`_option_cost`), then the first listed.
   - `GROUP` and `CHOICE` requirements go through `_pick_from_group`. It picks just enough courses to meet `min_courses`, `min_credits` and `min_areas` (areas come from `Course.areas`; `max_from_same_area` caps any one area). It prefers, in order: courses already credited, courses whose prerequisites are reachable, courses from a new area, then the listed order. A `GROUP` with neither `min_courses` nor `min_credits` takes every listed course.
   - A course claimed by one requirement can't satisfy another (for example, electives beyond the 400-level picks). Claims are per program in a `ClaimLedger` (`optimizer/core/claims.py`, shared with the audit): within a program there's no sharing, but `rules.may_share` lets majors share with each other without a limit, and a minor count a major's course up to `rules.within_major_minor_overlap` (UMD: 6 credits per minor, or the two largest shared courses if more, so 4+4 passes and 3+3+2 does not; a minor's `max_overlap_with_major` can also cap the course count). A course counts toward at most one minor. Minors spend that overlap only after truly free courses, and a major's GROUP prefers courses a later minor lists, so the minor can share them.
   - A requirement with `exclusive: false` (the CS Upper Level Concentration, which may overlap with a minor) doesn't claim its picks: they go in `shared`, and later GROUP/CHOICE/CATEGORY requirements prefer reusing them (`_free`), claiming them as they do. A non-exclusive CATEGORY prefers courses later requirements list (`listed_after`).
   - `CATEGORY` (`_select_category`) is a rule, not a list: any catalog course passing its filters (`pattern`, `departments`, `exclude_departments`, which also rejects courses cross-listed with those departments, the `min_level`/`max_level` number range, and `has_prerequisite`) counts toward `min_courses`/`min_credits`. The filter is `categories.category_matches`, shared with the audit; `pattern` and `departments` accept a course when it or any course cross-listed with it matches (CMSC460 counts as AMSC460). It prefers credited (or shared), then reachable, then later-listed courses (non-exclusive: any later requirement; exclusive: later programs whose overlap is unlimited, i.e. other majors), then unrestricted, then non-independent-study courses, then codes matching the filters themselves rather than through a cross-listing, then course code. "Reachable" counts courses from single-course requirements and groups needing every listed course (`mandatory`) as taken. Picks stay within `max_independent_study_credits` (`categories.within_limits`, shared with the audit; `rules.is_independent_study` goes by course name). With `single_department`, it compares each department's picks and takes the first that meets the minimums, ranked by fewest unreachable picks, then fewest restricted picks, then (non-exclusive only) the most picks a later requirement lists, then the most credited/selected courses already in that department, then name. The CS `statistics` (STAT4xx needing MATH141), `additional_math_stat` (MATH/STAT needing MATH141), specialization electives (CMSC 3XX/4XX) and Upper Level Concentration requirements are all CATEGORYs.
   - Multiple degrees: `UNIQUE_CREDITS` (each major needs `rules.MIN_UNIQUE_MAJOR_CREDITS` = 18 credits no major of another degree counts) is only a check in selection. GROUP and CATEGORY picks steer toward it: a course a major of another degree already claimed (`ClaimLedger.crosses_degree`) ranks with new courses, after them, and `_shareable_later` ignores other-degree majors. The audit's `_unique_credits` compares the courses each major's met requirements applied (`_Auditor.counted`, non-exclusive ones included).
   - `DISTRIBUTION` (the CS specializations' "at least 3 areas") claims nothing: it checks the areas (`Catalog.primary_area`) of the courses its program counts so far that pass its CATEGORY filters. `_pick_from_group` steers toward it: while a later DISTRIBUTION of the same program is short of `min_areas`, it prefers matching courses from areas the program lacks. A GROUP's `min_areas_ignore` areas don't count toward its own `min_areas`, and `mutually_exclusive` sets allow at most one pick each.
   - `CREDIT_HOURS` (`_select_electives`) adds free electives until its `min_credits` and `min_courses` are met. These requirements are filled after every other requirement, most specific (filtered) first, so upper-level picks also count toward the total. Credits counted so far come from `categories.credit_hours`, shared with the audit, plus `prior_credits` for unfiltered ones. Candidates must be offered, undergraduate (`rules.is_undergraduate`), pass the filters and not already be planned. Courses numbered below 100 (`rules.earns_degree_credit`) are never picked. They're preferred in this order: no restrictions, reachable prerequisites, not independent study, not under the upper-level CMSC cap, offered in the most terms, credits closest to `rules.TYPICAL_COURSE_CREDITS`, departments with the most planned/credited courses, then code. They're listed in `Selection.electives` and don't claim courses.
   - Minimum grades: a requirement's `min_grade` applies to it and its nested requirements, else its program's (`RequirementOwner.min_grade`, the minor's `min_grade`). `_have`/`_free` count a credited course only if its grade meets it; a GROUP/CHOICE then prefers another option, while a COURSE (or a benchmark course, `_retake_for_benchmarks`) is retaken. Retakes are in `Selection.retakes`; the optimizer keeps them although they're credited, and `_taking` (selected and not credited, or a retake) is what counts as planned for prerequisites.
   - After the requirements and before free electives, `_add_missing_prerequisites` adds courses selected courses need (as prerequisites or corequisites) that nothing else covers, including credited ones whose grade is below the prerequisite's `min_grade` (as retakes) (CS + RAS gets MATH246 for ENME480), taking for an OR the alternative already met, else the first whose own prerequisites can be met. They're listed in `Selection.prerequisites`.
   - `GEN_ED` (`_select_gen_ed`) first counts credited or already-selected courses whose gen-ed option covers the category. That reuse is how double counting happens, e.g. DS + DV, or DSNL → DSNS. If more is needed, it picks catalog courses in this order: no restrictions, then reachable prerequisites, then credits closest to `min_credits / min_courses`, then course code. The chosen option for each course is locked in a `GenEdLedger`.
2. **Drop completed courses** with `StudentProfile.has_completed`. "Completed" means `credited_courses()`: taken courses, AP *values*, and transfer *keys*.
3. **Order** with `_scheduling_priority`. Benchmark courses come first, earliest benchmark first (`_benchmark_deadlines`: the courses the audit applies to each benchmark from the selection; a prerequisite inherits the earliest deadline of what depends on it). Then courses that start the longest chain of required dependents. Ties go to courses offered in fewer terms, then to topological order. Requested courses' deadlines join the benchmark ones (`_request_deadlines`; `by_semester` N counts as `credits_completed` + N × the minimum preferred load). Free electives are then moved to the end, so they only fill room left by required courses, and requested courses no requirement counts and with no deadline just before them. `PrerequisiteGraph.topological_sort` breaks its own ties by input order.
4. **Greedy semester assignment** (`_assign_courses_to_semesters`) over `plan_terms`: `regular_semesters(program)` Fall/Spring semesters (8, or as many as the credits still needed take at the minimum preferred load, 10 for a double degree's 150), plus a Winter term between each Fall and Spring (`include_winter`) and a Summer between each Spring and Fall (`include_summer`). A course is added when all of these hold:
   - its prerequisites are met by courses from earlier semesters
   - its corequisites are met by courses from earlier semesters or this one; if not, `_corequisite_bundle` picks the planned courses that would meet them (for an OR, the highest-priority planned alternative), each takeable now (`_takeable`) with its own corequisites met by the group, and the course goes in only together with them (credits and the CMSC cap counted for the whole group)
   - it is offered that term
   - credits stay within the term's max (`rules.credit_load`: `preferred_credit_load` for Fall/Spring; `summer_max_credits`/`winter_max_credits`, capped by `rules.MAX_TERM_CREDITS` at UMD's 16 and 4), and Summer/Winter hold at most `summer_max_courses`/`winter_max_courses` courses (`rules.course_limit`, default 1: students usually take one course then; a corequisite group counts in full). The validator reports `Too many courses`.
   - `rules.py` allows it: at most 3 upper-level (300–499) CMSC courses per semester, and FSPW gen-eds only after 60 cumulative credits
5. **Balance** with `balance.balance_credits`: while some move narrows the gap between a heavier and a lighter semester, move one course from the heavier to the lighter (or swap it for one worth fewer credits, e.g. when a single move would drop an FSPW course below 60 prior credits). The credits moved must be less than the gap, so it terminates. Pairs go from the largest gap down. Moves of free electives come first, then single moves before swaps, then courses no later course needs, then the closest result, then codes. A move must keep the schedule valid (`balance.schedule_valid`: prerequisites from earlier semesters, corequisites from earlier or the same semester, offered terms, `credits_required_before`, max load, the upper-level CMSC cap), not raise either semester's difficulty above the harder of the two and the student's max, and keep every benchmark and request deadline the greedy plan met (`_deadlines_met`). It never adds or removes semesters.
6. **Solve** (`ScheduleOptimizer(..., use_solver=True)`, the default) with `solver.solve_schedule`: one CP-SAT model of the whole plan over `plan_terms`, hinted with the balanced greedy schedule. Hard: at most one offered term per course, prerequisites strictly earlier and corequisites earlier or same term (condition trees as literals; credited courses and equivalents count), term credit max, Summer/Winter course limit, the upper-level CMSC cap, `credits_required_before`. Objective weights (module constants): unplaced course 100000, missed benchmark/request deadline 10000 (benchmark deadlines from `_benchmark_deadlines` plus `by_credits`; `by_semester` counted in Fall/Spring semesters), last term used 1000 per term, Fall/Spring shortfall below the preferred minimum 30 per credit, spread between used Fall/Spring semesters 40 per credit, difficulty over the max 2 per 0.1, each term a non-elective course waits 1. It runs on one worker, seed 0, `max_deterministic_time` 10, so it is deterministic. `_plans` keeps the greedy schedule if the solver finds nothing, places fewer courses, or meets fewer deadlines (`_no_worse`). `generate_multiple_scenarios(program, n, min_changes)` re-solves with `avoid=` the plans so far (`_Model.differ_from`: at least `min_changes` of each earlier plan's course-term placements must change) and keeps an alternative only if it is `_no_worse` than the first and finishes no later (`_finish`); it stops at the first that fails. Alternatives take the same selected courses. Tests of greedy-only behaviour pass `use_solver=False`.
7. **Validate** with `ConstraintValidator.validate_schedule`. Credited courses count toward prerequisites. Errors, and missed benchmarks, are only logged as warnings (`logging`, never configured by the library); the schedule is still returned.

**Requirement audit** (`optimizer/core/audit.py`): `audit_requirements(courses, requirements, catalog) -> AuditReport` is the one authority on whether requirements are met, for any list of courses (generated or hand-written). `ScheduleOptimizer.audit(program, schedule=None)` audits the schedule plus credited courses (credited only without a schedule). With `grades` (code -> grade of courses taken; `ScheduleOptimizer.audit` passes the student's, minus courses the schedule retakes), a course counts toward a requirement only if it meets the requirement's `min_grade` (inherited by nested requirements, else the program's). Each `RequirementResult` gives `satisfied`, the `applied` courses, `credits` and a `reason` when unmet. It follows the selection rules above (equivalents count, GROUP minimums/areas, CATEGORY filters, single department and independent study cap, no double counting across COURSE/GROUP/CHOICE/CATEGORY except that a non-exclusive requirement's courses stay available to later ones and a minor may share with a major through the `ClaimLedger` when `owners` are given, preferring unshared courses; gen-eds reuse courses with option locking) using a deterministic greedy pass whose limits are in the module docstring. Plan courses a later CATEGORY matches count as demanded by it, so earlier requirements leave them for it when they can. `CREDIT_HOURS` sums the credits of every plan course passing the CATEGORY filters (no filters means every course) without claiming them. `ScheduleOptimizer.audit` passes `prior_credits` (`categories.prior_credits`: `credits_completed` minus the credited courses the catalog knows), and those count only toward unfiltered CREDIT_HOURS. `MajorRequirements.credit_requirements()` turns `min_credits` and `min_upper_level_credits` into `total_credits`/`upper_level_credits` requirements; `StudentDegreeProgram.credit_requirements()` keeps the highest of each across majors, and `get_all_requirements()` appends them after the gen-eds. `min_major_credits` isn't checked and CS doesn't set it: the earlier value of 54 "CS credits" had no UMD source. The CS plan meets every requirement, at about 121 credits.

**Alternatives** (`optimizer/core/alternatives.py`): `ScheduleOptimizer.course_alternatives(program, schedule, courses=None)` maps each planned course to the courses that could replace it in the same term with nothing else moving (`find_alternatives`; rules in the module docstring). Candidates are what every satisfied requirement applying the course would accept (`_accepts`: listed codes with equivalents, CATEGORY/filtered CREDIT_HOURS matches, gen-ed options; unfiltered CREDIT_HOURS and DISTRIBUTION accept anything), not excluded, planned, credited or credit-conflicting. A candidate is kept if `balance.schedule_valid` holds after the swap, the term's difficulty doesn't rise past the student's max or its old value, and `ScheduleOptimizer._audit` still meets every row it met (requirements, benchmarks, requests). Sorted unrestricted first, then code. A whole CS plan takes ~7 s (gen-ed and elective pools are large), so pass `courses` when only some are needed. Re-planning with a swap is `excluded_courses` + `requested_courses`.

**Benchmarks**: `MajorRequirements.benchmark_requirements()` turns `benchmarks` into `(credits, GROUP)` pairs with id `{major_code}_benchmark_{credits}`; `StudentDegreeProgram.benchmark_requirements()` combines both majors'. `audit_benchmarks` audits each on its own against the credited courses plus the semesters through the one where cumulative credits (`credits_completed` plus planned) first reach `credits`. `ScheduleOptimizer.audit` appends those results after the requirements', then `audit_requests` rows (`requested_{code}`: credited or planned by the deadline; `by_semester` counts Fall/Spring terms from the first planned semester, so empty semesters still count), so its report has more rows than `get_all_requirements()`. Missed benchmarks and request deadlines are logged as warnings when planning.

`GenEdLedger` (`optimizer/core/gen_eds.py`) is the single implementation of gen-ed option locking, used by both the selector and the audit. Don't reimplement "does this course count toward category X" elsewhere.

UMD policy rules (the upper-level CMSC limit, FSPW at 60 credits, FSPW after an FSAW course (`GEN_ED_PREREQUISITES`, which `DataLoader.load_catalog` adds as an OR of the catalog's FSAW courses to every FSPW course whose prerequisites don't already name one), DSNL→DSNS, which course names mean independent study, which programs may share courses and the major/minor overlap cap, the multiple-degree credits and unique credits) live in `optimizer/core/rules.py`. The scheduler applies them and `ConstraintValidator` re-checks the cap and the credit minimums, counting `StudentProfile.credits_completed`. Add new policies there rather than in `optimizer.py` or `constraints.py`.

### Catalog and course equivalence
`optimizer/models/catalog.py` `Catalog` is a read-only `Mapping[str, Course]`. Everything that takes a catalog also accepts a plain dict; `ScheduleOptimizer` and `ConstraintValidator` wrap it with `Catalog.of(...)`. Honors and base versions (`XXXX100H` ↔ `XXXX100`) and cross-listed courses (detected by an *identical course name*, indexed once in `__init__`) are treated as the same course:
- `Catalog.equivalents` / `has_equivalent_in`, and `dedupe_equivalents`, which keeps order but prefers the non-honors version
- `StudentProfile.has_completed` has no catalog, so it only handles the honors/base pair (shared `honors_pair` helper)

`Catalog.course_number` (`CMSC498A` → 498), `Catalog.department` (`CMSC498A` → `CMSC`) and `primary_area` (`Course.areas[0]`, else an equivalent's, so AMSC460 has CMSC460's area) are the other lookup helpers. `ClaimLedger` keys claims by equivalence class, so a cross-listed course is one course across programs. `Catalog.requires(code, prereq)` says whether every prerequisite path of `code` goes through `prereq` (transitively; OR alternatives missing from the catalog are ignored, cycles count as not requiring). Policy built on them, like the 300–499 cap, belongs in `rules.py`.

### Gen-ed data model
`Course.gen_ed_options` is a list of alternative option groups. For example, `[['DSHS'], ['DSHU','DVUP']]` means a student counts the course *either* as DSHS *or* as DSHU+DVUP, not all three. `gen_ed_categories` is a flattened legacy field. Use `Course.get_gen_ed_option_for_category` rather than reading `gen_ed_categories`.

### Prerequisites
`PrerequisiteCondition` is a tree:
- `COURSE`: *every* listed course is required, each meeting `min_grade` if one is set
- `OR`: any course in `courses`, or any of its nested `conditions` (e.g. "BSCI180 or (BSCI161 and BSCI171)")
- `AND`: all of the nested `conditions`

`Course.corequisites` uses the same trees. A corequisite is met by a course taken in an earlier semester or the same one: a course whose corequisite isn't taken yet goes in the same semester as it. `Schedule.validate` reports `Corequisites not met`. Curated files list corequisites as codes (each required); generated departments parse Testudo's corequisite text with `parse_prerequisite_text` (kept as `corequisite_text`).

Prerequisites are checked against real grades: `StudentProfile.grades()` for credited courses (best grade per course; AP "P", transfer grade or "TR"), and "A" for courses placed in the plan. The grade scale is `optimizer/models/grades.py` (`meets_minimum`, `earns_credit`: F/W/I earn nothing, so `credited_courses()` leaves them out; P/S/CR/TR meet any minimum). `ConstraintValidator.check_prerequisites`/`Schedule.validate` take codes (each an A) or code -> grade. The graph adds an edge for *every* course in an OR, so topological ordering is conservative.

`DataLoader` adds `rules.PREREQUISITE_SUBSTITUTES` to every prerequisite it loads: a prerequisite naming MATH240 or MATH246 also accepts MATH341, and MATH241 also accepts MATH340 (departments generally accept the honors sequence). Add such policies to that table, not to course data.

Prerequisites that apply only to a program's students go in that major's or minor's `prerequisite_overrides` (course → prerequisite list in the course-file format, parsed like the catalog's, substitutes included). `StudentDegreeProgram.prerequisite_overrides()` combines them (several programs overriding one course become an OR of their lists), and `ScheduleOptimizer.for_program` swaps them into a derived catalog (`Catalog.with_prerequisites`) that `select_courses`, `optimize_schedule` and `audit` use; the optimizer's own `course_catalog`, `validator` etc. keep the catalog's prerequisites, so validate a program's schedule with `for_program(program).validator`. `minors/RAS.json` overrides ENAE450, ENEE467 and CMSC477 (catalog: CMSC420 or CMSC421 and linear algebra; RAS: linear algebra and ENEE467).

`Course.credit_only_one_of` is Testudo's "Credit only granted for" list. `Catalog.credit_conflicts` pairs a course with each course on its *own* list (MATH341 overlaps MATH240 and MATH246, which don't overlap each other). The selector's `_taken_or_planned` treats a course overlapping a credited or planned one as taken, so plans never hold both MATH240 and MATH461, or MATH340 and MATH241; `_planned` (equivalents only) is what meets prerequisites.

`optimizer/data/prerequisite_text.py` `parse_prerequisite_text` turns Testudo's prerequisite sentences into these trees; its module docstring has the reading rules (`;`/"; or" clauses, "and" binding looser than "or", "1 course from (...)" as OR, alternatives naming no course dropped, so "or permission of instructor" still requires the courses).

### Data and loading
- `optimizer/data/loader.py` `DataLoader(data_dir)` reads `data_dir/courses/{DEPT}.json`, each shaped as `{"courses": [...]}`.
- Prerequisites can be plain course-code strings or `{type: course|or|and, ...}` dicts (Testudo sentences go through `parse_prerequisite_text` when department files are generated).
- `load_major`/`load_minor` read `data_dir/majors/{CODE}.json` and `data_dir/minors/{CODE}.json`. Each requirement object's keys map directly onto `Requirement` dataclass fields, and `type` is a `RequirementType` value. Requirements can be nested inside `courses`/`choices`, and `{"code": ...}` is shorthand for a single-course requirement. `majors/CMSC.json`, `majors/MATH.json` and `minors/RAS.json` exist so far. `Requirement.__post_init__` raises `ValueError` if a type's own field is missing (COURSE→`course_code`, CHOICE→`choices`, GROUP→`courses`, which may be `[]`, GEN_ED→`gen_ed_category`, CATEGORY→`min_courses` or `min_credits`, CREDIT_HOURS→`min_credits`, DISTRIBUTION→`min_areas`, UNIQUE_CREDITS→`min_credits`).
- Tracks (specializations) are optional; most majors won't have them. A major file with `tracks` keeps the shared requirements at the top level and each track's under `tracks.{name}`. `load_major(code, track=None)` uses `default_track` when no track is given, and raises `ValueError` for an unknown track (or any track on a major without them). A track requirement replaces the shared one with the same `id`/`code` in place; others are appended to their section. Other track keys (`major_name`, `concentration`, ...) replace the shared value, and `MajorRequirements.track` names the track. `major_tracks(code)` lists them, default first. `majors/CMSC.json` has `general` (default), `cybersecurity`, `data_science`, `machine_learning` and `quantum_information`, from undergrad.cs.umd.edu. `majors/MATH.json` has `traditional` (default), `statistics` and `applied`, from www-math.umd.edu/course-requirements.html; the Secondary Education track isn't modeled (its education courses are only named generically there). Its one-year sequence is a non-exclusive CHOICE of GROUPs, so its courses also count toward the other upper-level requirements, and "eight 400-level MATH/AMSC/STAT courses" is a CREDIT_HOURS with `min_courses`. Its programming course (one approved programming/computation course) is non-exclusive so CMSC131 can also count toward the CMSC 131-132-216 supporting sequence (the page doesn't say; an assumption). The honors MATH340-341 is an alternative to MATH240-241-246: linear algebra accepts MATH341, multivariable MATH340, and the ODE requirement (track-specific, overridden by id) MATH341; the ODE requirement comes first and is non-exclusive so MATH341 can count for both. Its Upper Level Concentration is the major's `concentration`, so it comes after every track requirement (UMD: courses used for the major can't count toward the ULC).
- Gen-eds are university-wide, not part of a major: `load_gen_eds("UMD")` reads `data_dir/gen_eds/UMD.json` (`{"requirements": [...]}`). Callers pass the result as `StudentDegreeProgram(gen_ed_requirements=...)`, which `get_all_requirements()` puts last, so gen-eds can reuse courses already picked for the major.
- The optimizer silently skips requirements whose courses aren't in the catalog.
- `sample_data/courses/` holds the catalog the optimizer actually uses. `CMSC.json` and `MATH.json` are hand-curated (`CMSC.json` entries whose `notes` say "Prerequisites rebuilt", CMSC425/436/457/471–474, came from the flat Academic Catalog lists and are reconstructions to verify). `STAT`, `AMSC`, `PHYS`, `ENEE`, `ENME`, `ENAE`, `ENES`, `BIOM` and `MATH_generated` (the MATH courses `MATH.json` lacks) are generated (`"generated": true`) by `scrapers/generate_departments.py`, and `GENED.json` by `generate_gened.py`. `DataLoader.load_catalog()` (alias `load_all_courses()`) assembles them into a `Catalog`: GENED first, then department files in name order overriding its entries. A department entry with no `gen_eds` keeps GENED's `gen_ed_options`/`gen_ed_categories` (that is how MATH140 gets FSAR/FSMA).

### Data acquisition (`scrapers/`)
- `scrape_testudo.py`: scrapes the Testudo Schedule of Classes for a term (default `202601`) into `data/testudo_courses/{dept}.json/.md` (or `--output`). Besides the flat `prerequisites` code list it keeps `prerequisite_text`, `corequisite_text`, `credit_only_granted_for`, `formerly` and `additional_info`, reading every text block of a course (Testudo puts the description and each labelled field in separate blocks). This is the source of `gen_eds`. Usage: `python scrapers/scrape_testudo.py CMSC MATH`, `--all` (department list from `data/departments/departments.md`), `--term`, `--delay`, `--format`. More detail in `scrapers/README.md`.
- `generate_departments.py DEPT...`: builds `sample_data/courses/{DEPT}.json` from `data/testudo_terms/{term}/{dept}.json` (one `scrape_testudo.py --term T --output data/testudo_terms/T` run per term; Fall 2025 to Spring 2027, Winter 2026, Summer 2026 and Winter 2027 included, are scraped for the generated departments and CMSC/MATH; `scrape_testudo.py` saves a department with no courses that term as an empty file, so the generators know the term was checked). Undergraduate courses only; `offered` is every season a course was listed in; `prerequisites` come from `parse_prerequisite_text` (raw text kept as `prerequisite_text`); `credit_only_granted_for` is copied; permission the prerequisite text *requires* ("; and permission of ...", not "or permission of instructor") is added to `restrictions`. The curated `MATH.json` and `CMSC.json` entries got their `credit_only_granted_for` lists from the same Testudo data (CMSC460/466 by hand). Courses a hand-curated file defines (e.g. MATH.json's STAT courses) are left out. When the department itself has a hand-curated file, the rest go to a `{DEPT}_generated.json` supplement (it loads after the curated file); `--force` replaces the curated file instead. `--offered-only CMSC MATH` instead rewrites just the curated files' `offered` lines from the scrapes (each course looked up in its own department's terms, so MATH.json's STAT courses use `stat.json`; Summer/Winter, which no scraped term covers, and courses no term lists keep their curated values; the terms used are recorded as `offered_terms`). CMSC and MATH are scraped for the same four terms. The Academic Catalog site was unreachable when these were built, so courses never offered in the sampled terms are missing.
- `scrape_umd_catalog.py`: scrapes the Academic Catalog into `data/scraped_courses/`. It has fuller descriptions but no gen-ed data.
- `generate_gened.py`: rebuilds `sample_data/courses/GENED.json` from every course in `data/testudo_courses/*.json` that has gen-eds. It overwrites as soon as it runs; the committed file is exactly its output (the FSPW courses' ENGL101 prerequisite comes from `rules.GEN_ED_PREREQUISITES`, not the file), so keep it that way: put policies in `rules.py` rather than editing the file, and review `git diff` after a rebuild for scrape changes.
- Default paths in these scripts are relative to the repo root, so run them from there.

## Notes
- Besides the courses requirements call for, plans only add the free electives needed to reach the major's `min_credits`. Electives avoid courses under the per-semester upper-level CMSC cap, so they don't crowd required CMSC courses out of the last semesters; the CS plan gets a few lower-level courses this way. Unit tests that build a `MajorRequirements` set `min_credits=0` to keep electives out.
- `MajorRequirements.benchmarks` (limited-enrollment checkpoints, `{"45": [...]}` in JSON) only holds the CS 45/75-credit benchmarks. Their `min_grade` is checked (`audit_benchmarks(grades=...)`, ignoring the old grade of a course retaken by the deadline); the 2.0 GPA isn't.
- Schedules sort chronologically within a calendar year: Winter, Spring, Summer, Fall (`schedule.TERM_ORDER`). Fall *Y* is followed by Winter and Spring *Y+1*. Wherever the planner counts or ranks offered terms (selection filters, elective and scheduling preferences), it uses `rules.terms_offered`: only the terms the student's plan has, so Summer offerings don't change a Fall/Spring-only plan. `balance_credits` evens out Fall/Spring semesters only, and the audit's `by_semester` counts Fall/Spring semesters, a Summer or Winter counting with the semester after it.
